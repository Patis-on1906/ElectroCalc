# Технический анализ и исправления ElectroCalc_v6

## 1. Почему исходная версия создавала лишние узлы

Главная проблема была не в отображении списка узлов, а в модели построения графа в `MainWindow.xaml.cs`.
Исходная логика фактически регистрировала каждый отдельный элемент как отдельную `CircuitBranch` между двумя `CircuitNode`. Поэтому соединение `R1 — провод — R2` неизбежно превращалось в две ветви с промежуточным расчётным узлом, хотя электрически это одна последовательная ветвь.

Исправление: расчётный граф теперь полностью строится заново из логических концов проводов:

1. Все концы, соединённые идеальными проводами, объединяются Union-Find в один conductor-net.
2. Каждый элемент становится ребром между net своего PortA и net своего PortB.
3. Все net степени 2 сворачиваются как последовательные точки.
4. `CircuitNode` создаётся только для существенных точек: разветвлений/концов, а для чистого кольца выбираются две служебные опорные точки.
5. Максимальная последовательная цепочка элементов между существенными узлами становится одной `CircuitBranch`.

В результате цепочка `узел A — R1 — R2 — E1 — узел B` хранится как одна ветвь с тремя элементами.

Дополнительно устранена зависимость топологии от координат и порядка рисования. Перемещение подключённого элемента больше не уничтожает его электрические связи: провода хранят логические `PortKey`, а координаты нужны только для отрисовки.

## 2. Направление элементов внутри составной ветви

После сворачивания последовательных элементов появилась важная задача: визуальное направление PortA→PortB отдельного элемента может не совпадать с направлением расчётной ветви Start→End.

В `CircuitBranch` добавлено направление каждого элемента (`+1/-1`). Оно используется для:

- знака ЭДС;
- знака заданного тока источника J;
- отображения `LastCurrent` на конкретном элементе;
- клонирования схемы в методе эквивалентного генератора.

Без этого схема с развернутым источником давала бы неверный знак даже при правильной топологии.

## 3. Единая DC-модель ветви

Добавлен `Core/Solvers/DcBranchModel.cs`. Все методы теперь используют одно соглашение:

`U = φstart − φend = R·I + E`.

Для установившегося постоянного тока:

- R — обычное сопротивление;
- E — ЭДС, внутреннее сопротивление учитывается последовательно;
- J — идеальный источник тока, задающий ток ветви;
- C — разрыв (`I = 0`);
- L — короткое замыкание (`U = 0` для чистой L-ветви).

Нулевое сопротивление и идеальный источник напряжения больше не «теряются» из расчёта, а обрабатываются как идеальная ветвь напряжения.

## 4. Исправления метода узловых потенциалов

Исходная реализация имела несогласованный знак эквивалентного источника для ветви E+R. При принятом направлении тока должно быть:

`I = (φstart − φend − E) / R`.

Отсюда в правой части узловой системы вклад ЭДС равен `+gE` для Start и `−gE` для End.

Решатель переписан в форме Modified Nodal Analysis (MNA):

- проводимости R/E штампуются в матрицу;
- идеальные E, L и R=0 получают дополнительную неизвестную тока и уравнение `φstart−φend=E`;
- J штампуется как заданный ток;
- C исключается как разрыв;
- перед решением проверяется связность активной DC-схемы;
- в пошаговом выводе показываются соглашение знаков, матрица, ход Гаусса, потенциалы, токи и баланс мощности.

## 5. Исправления метода контурных токов

В исходной версии знак взаимного сопротивления общих ветвей был противоположным требуемому. Для фундаментальных контуров коэффициент общей резистивной ветви должен добавляться как:

`R · dir_i · dir_j`.

Правая часть по ЭДС при соглашении `U=R·I+E` формируется как:

`−Σ(dir·E)`.

МКТ теперь:

- строит остовное дерево и фундаментальные контуры;
- корректно учитывает знак общей ветви в двух контурах;
- поддерживает идеальные источники тока через дополнительные неизвестные `U_J` и ограничения на ток ветви (обобщённый supermesh);
- восстанавливает физические токи ветвей из контурных токов;
- восстанавливает узловые потенциалы из найденных напряжений ветвей;
- рассчитывает напряжение на открытых C-ветвях по потенциалам их концов.

## 6. Метод эквивалентного генератора

Исправлены три существенных места:

- при удалении нагрузки и клонировании сохраняется ориентация каждого элемента;
- E при деактивации заменяется внутренним сопротивлением, идеальный E — КЗ; ветвь с идеальным J — разрыв;
- `Rэкв` ищется тестовым источником **1 А**, а не 1 В. Это принципиально важно для случая `Rэкв=0`: источник 1 В конфликтовал бы с идеальным КЗ, тогда как источник 1 А даёт корректное нулевое напряжение.

После расчёта Тевенина выполняется независимый полный расчёт исходной схемы МУП и в решении показывается расхождение тока нагрузки.

## 7. Мощность и отображение результата

Мощность считается по пассивному соглашению знаков:

`Pветви = U·I`.

Резистивные потери всегда `R·I²`. Остаток мощности относится к идеальным источникам. Поэтому для источника корректно разделяются `PowerConsumed` и `PowerGenerated`.

В таблице UI столбец мощности теперь знаковый: `+` означает потребление, `−` — генерацию. Отдельно показываются суммы генерируемой/потребляемой мощности и относительная проверка баланса.

## 8. Дополнительные исправления UI и данных

- Ввод чисел принимает и `,`, и `.`.
- Запрещены NaN/Infinity и отрицательные R/C/L или внутренние сопротивления.
- Выбранная нагрузка для Тевенина сохраняется при пересборке графа.
- Старый результат инвалидируется после изменения схемы/параметров, поэтому нельзя случайно экспортировать расчёт уже изменённой схемы.
- Точку соединения теперь можно выбрать ПКМ и удалить; раньше ветка удаления junction фактически была недостижима из UI.
- Ошибочный расчёт больше не окрашивает нулевой «баланс мощности» как успешный.

## Исправление T-соединений проводников (ревизия 2)

Обнаружена дополнительная проблема визуальной топологии: `WireVisual` логически объединял только свои два конца. Поэтому вертикальная шина могла визуально проходить через порт резистора, но порт оставался в другом электрическом net. На типичной мостовой схеме это приводило к четырём визуально правильным узлам, но к несвязному расчётному графу.

При пересборке графа теперь выполняется геометрическая нормализация соединений: если порт элемента или явная точка соединения лежит на сегменте существующего провода (с небольшим допуском), терминал объединяется с net этого провода. Простое пересечение двух проводов без терминала/точки по-прежнему не означает соединение.

Также сообщение NodePotentialSolver о несвязности больше не утверждает, что причиной является конденсатор, если в схеме нет DC-разомкнутых ветвей. Набор элементов схемы произвольный: для расчёта постоянного тока не требуется присутствие R/E/J/C/L всех типов одновременно.


## Исправление v3: активная ветвь в методе Тевенина и баланс мощностей

- Метод эквивалентного генератора теперь допускает выбранную последовательную ветвь `E + R` (а также `R/L`).
- Для активной нагрузки используется `Iн = (Uхх - Eн)/(Rэкв + Rн)` при соглашении `U = R I + E`.
- Потребляемая мощность теперь означает именно потери в сопротивлениях: `ΣP_R = Σ I²R`.
- Мощность источника хранится со знаком генерации: `Pист = -E I` для идеального источника ЭДС при принятой ориентации; положительный знак означает генерацию, отрицательный — поглощение.
- Баланс проверяется как `ΣPист(нетто) = ΣP_R`. Источник, работающий в режиме приёмника, уменьшает нетто-генерацию, а не попадает в колонку потребительской нагрузки.

## Дополнение v5

Добавлен `KirchhoffLawSolver`, формирующий классическую систему в токах ветвей: `N-1` уравнений KCL, `B-N+1` фундаментальных KVL и, при наличии идеальных источников тока, дополнительные уравнения заданного тока с неизвестными напряжениями их ветвей. Численное решение выполняется тем же устойчивым решателем Гаусса, но в пользовательском выводе показываются только исходная символическая система, подстановка номиналов и итоговые токи.

`MeshCurrentSolver` теперь разделяет символическое составление МКТ и числовую подстановку; внутренние шаги исключения Гаусса не добавляются в `CalculationResult.Steps`.

`PowerBalanceFormatter` централизует энергетический вывод для МКТ, МУП, метода Кирхгофа и эквивалентного генератора. Символический баланс строится по отдельным элементам: источники входят как знаковые `±I·E`, пассивные потери — как `I²·R` (включая заданные внутренние сопротивления источников).

Нумерация существенных `CircuitNode` визуализируется на `SchematicCanvas`. Метки пересоздаются после каждой пересборки топологии, поэтому совпадают с номерами узлов в решателях и экспортируемом решении.

## v7 — последовательность метода эквивалентного генератора

Метод Тевенина перестроен в учебной последовательности. После удаления выбранной ветви программа ищет кратчайший путь между её зажимами через ветви с определяемым напряжением и записывает для образованного контура второй закон Кирхгофа в виде `Uхх - ΣUветвей = 0`. Токи в этой записи обозначаются `I1х, I2х, ...` по номерам исходных расчётных ветвей.

Далее разомкнутая схема рассчитывается тем же `NodePotentialSolver`, что и обычный МУП. В решение Тевенина переносятся выбор опорного узла, символическая система, численная подстановка, узловые потенциалы и токи ветвей; промежуточные шаги Гаусса и баланс мощности вспомогательной схемы не выводятся. После этого найденные токи подставляются в исходное уравнение Кирхгофа и из него вычисляется `Uхх`.

Затем определяется `Rвх` при деактивированных независимых источниках тестовым током 1 А и вычисляется ток возвращённой нагрузки: `Iн=(Uхх-Eн)/(Rвх+Rн)`. Полный МУП исходной схемы выполняется только как скрытая внутренняя проверка и для заполнения таблицы ветвей; отдельным шагом решения он не показывается.

## v9 — архитектура DC/AC и комплексная модель

### Цель этапа

AC-функционал не добавляется отдельным набором копий DC-решателей. Введён общий слой настроек анализа и фазорная модель электрических величин, чтобы последующие методы (мощности, Тевенин, потенциальные и векторные диаграммы) использовали одну математическую основу.

### Новые сущности

`CircuitAnalysisSettings` хранит `Mode`, `FrequencyHz` и вычисляет `AngularFrequency`. `CircuitElement` хранит `PhaseDegrees`; в AC поле `Value` источника является RMS, а `SourcePhasor()` преобразует RMS/фазу в `System.Numerics.Complex`.

`SteadyStateBranchModel` формирует эквивалент ветви для выбранного режима и использует единое соглашение `U = Vstart - Vend = Z*I + E`. В AC вычисляются `R`, `jωL`, `1/(jωC)`. В DC сохраняются физические правила установившегося режима: C — разрыв, L — короткое замыкание.

`ComplexLinearSystemSolver` реализует комплексный метод Гаусса с частичным выбором главного элемента по модулю комплексного коэффициента.

### Совместимость модели результатов

`CircuitNode`, `CircuitBranch`, `CircuitElement` и `BranchResult` получили фазорные поля. Старые `double`-свойства оставлены как совместимый интерфейс действительной части для DC-кода. Это позволяет поэтапно мигрировать решатели без одновременного переписывания МЭГ, расчёта мощности и потенциальной диаграммы.

### Первый работающий AC-контур

На этом этапе AC подключён к МУП и МКТ. Оба решателя получают `CircuitAnalysisSettings`; в AC формируют и решают комплексную систему, а результаты показываются в прямоугольной и полярной форме. DC по-прежнему идёт через ранее проверенный путь этих решателей, что уменьшает риск регрессии существующих лабораторных расчётов.

### Ограничение этапа

На этапе v9 баланс комплексной мощности P/Q/S, AC-Тевенин, AC-уравнения Кирхгофа и диаграммы ещё не были подключены. В v10 добавлены P/Q/S и численные данные для векторных диаграмм. В v11 добавлены AC-Тевенин, символические законы Кирхгофа и восстановление мгновенных функций; AC-потенциальная диаграмма намеренно не реализуется.

## v10: общие инженерные сервисы поверх DC/AC-модели

### 1. Почему короткий трёхветвевой расчёт реализован детектором, а не жёстким методом

Упрощённый расчёт является свойством топологии, а не новым фундаментальным методом. `ThreeBranchSimplifiedDetector` проверяет граф после сворачивания последовательных точек. Поддерживается строго распознаваемый случай: два существенных узла, три активные ветви, две пассивные ветви с конечными ненулевыми импедансами и одна питающая ветвь. Это исключает неверное применение правила деления токов к произвольным трёхветвевым схемам с несколькими источниками.

Расчёт выполняется на `System.Numerics.Complex`: `Zэкв = Z1*Z2/(Z1+Z2)`, затем определяется общий ток нагрузки и `I1 = Iобщ*Z2/(Z1+Z2)`, `I2 = Iобщ*Z1/(Z1+Z2)`. В DC все мнимые части равны нулю.

### 2. Универсальный баланс комплексной мощности

Для ветви используется терминальная мощность по пассивному соглашению `Sветв = U*conj(I)`. Пассивная часть ветви имеет `Sпасс = |I|²*Zпасс`. Знаковая генерация источников ветви определяется как `Sист = Sпасс - Sветв`. Это особенно важно для идеального источника тока: его напряжение не задаётся самим элементом, а определяется всей схемой, поэтому остаточный энергетический способ устойчивее попытки вычислять мощность источника по заранее известной ЭДС.

Итоговая проверка: `ΣSист = ΣSпотр`, одновременно проверяются активная и реактивная составляющие. Каждая строка результата также имеет `P=Re(U*conj(I))`, `Q=Im(U*conj(I))`, `|S|`.

### 3. Векторные данные как отдельный слой представления

`VectorDiagramDataSolver` использует результат общего МУП и не содержит собственного электрического решателя. Поэтому он автоматически наследует дальнейшие улучшения основной модели. Сервис формирует: фазоры ветвей; напряжения отдельных элементов; ориентированные напряжения каждого найденного контура; ориентированные наружу токи каждого существенного узла. Для каждого фазора выводятся алгебраическая и показательная формы. Графическое построение намеренно отделено от численного слоя и может быть добавлено позже без изменения решателей.


## v11: расширение установившейся AC-модели

### AC-законы Кирхгофа

`KirchhoffLawSolver` теперь принимает `CircuitAnalysisSettings`. DC-путь сохранён, AC-путь строит ту же топологическую систему на `SteadyStateBranchModel`. KCL не меняет структуры, а KVL использует `Z̲I̲+E̲`. Ветвь идеального источника тока по-прежнему входит в KVL через неизвестное напряжение `U̲_J`, а её ток задаётся отдельным уравнением. Решение системы намеренно не выполняется — режим служит для учебной записи общего вида.

### Комплексный Тевенин

В AC метод эквивалентного генератора использует выбранную ветвь как нагрузку с `Z̲н` и `E̲н`. После удаления ветви ищется путь, допускающий запись напряжения через импедансы, токи и источники. `U̲хх` вычисляется из KVL и независимо проверяется как разность комплексных узловых потенциалов. Для `Z̲вх` независимые источники деактивируются, затем между зажимами подключается тестовый источник тока 1∠0° А, направленный так, чтобы ток исследуемой сети был A→B; `Z̲вх=U̲тест/I̲тест`. Итоговый ток сверяется с полным комплексным МУП исходной схемы.

### Мгновенные функции как слой представления

`InstantaneousWaveformFormatter` не участвует в электрическом решении. Он преобразует уже найденные RMS-фазоры в временную форму по единому соглашению `x(t)=sqrt(2)|X|sin(ωt+φ)`. Благодаря этому функция повторно используется МУП, МКТ, МЭГ, трёхветвевым упрощением и генератором векторных данных и не дублирует математику решателей.

## v12 — базовый трёхфазный слой

Трёхфазный режим реализован отдельным `ThreePhaseCircuitSolver` поверх общей RMS/Complex инфраструктуры. Электрическая роль элемента задаётся `CircuitElement.PhaseAssignment`; это намеренно отделено от геометрии холста, чтобы будущие инструменты (автопостроение, измерительные приборы, несимметричные нагрузки) могли использовать ту же фазную модель. Для звезды без N используется расчёт смещения нейтрали по комплексным проводимостям. Для Δ рассчитываются токи AB/BC/CA и затем линейные токи A/B/C. JSON повышен до version 3 и сохраняет параметры соединения, N и фазные назначения.
